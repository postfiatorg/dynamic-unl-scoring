# Scoring Prompt v11 — Minimum Safe Version

`prompts/scoring_v11.txt` replaces `scoring_v10.txt` as the active scoring prompt, shipping together with one collector change: a new setting, `MINIMUM_SAFE_VERSION`, names the oldest `postfiatd` release without a known security hole, the collector checks every validator's `server_version` against it (`scoring_service/server_version.py`, `check_minimum_safe_version` in `scoring_service/services/collector.py`), and the result is carried on the `ValidatorProfile` evidence model as `fails_minimum_safe_version` and rendered into every validator entry — always present, as `true` or `false`. The prompt sets the software sub-score of a validator that fails the check to exactly 0. `PROMPT_VERSION` moves to `v11` and the setting is recorded in every execution manifest under `code.collector.parameters.minimum_safe_version` (`null` when the rule is disabled). Score formula v1, its weights, the parser, the selector, and churn control are unchanged; `scoring_v10.txt` is retained on disk for audit; validator sidecars require no action because they replay the foundation's frozen `model_request.json` verbatim.

## Motivation

The September 2026 manifest flood (`postfiatd/docs/MANIFEST_FLOOD_HOTFIX.md`) and the remote crash closed in 1.0.8 showed that an outdated validator is a network risk, not only a sign of a slow operator: 1.0.4 nodes stored and re-served the flood, and one malformed validation stops any node older than 1.0.8. Scoring did not reflect that. In testnet round 23 (2026-09-15), two days after the flood fix shipped as 1.0.6, validators still on 1.0.4 received a software sub-score of 95 against 100 for 1.0.6. Software carries 10 of 100 formula weight, so missing the fix cost half a point, and 13 of the 20 UNL seats stayed on 1.0.4.

The model cannot close that gap on its own. It sees version numbers, not release notes, so it cannot tell a security release from a cosmetic one, and it is unreliable at ordering version strings (`1.0.10` against `1.0.8`). The verdict is therefore computed by the service and handed to the model as a boolean.

The rule lowers a sub-score instead of removing the validator from the round, deliberately. A failing validator is still scored, stays visible with a reasoning string that names the penalty, and can still hold a seat when too few safe validators exist to fill the list. The rule prefers safe validators without ever shrinking the UNL: on round 23 a hard exclusion would have cut the UNL from 20 seats to 11. The cost is that the rule is a strong preference, not a guarantee — software weight caps the penalty at 10 final-score points, and churn control still requires a challenger to clear the incumbent by the score gap.

## The v11 changes

1. **Verdict propagation.** The collector checks validators after the existing version exclusion filter. A validator passes only when its version is readable and not older than the minimum: a pre-release sorts below its final release (`1.0.8-rc1` fails a minimum of `1.0.8`), build metadata is ignored, and components compare as numbers. A missing or unreadable `server_version` fails — a validator that cannot show its version cannot be shown to be safe, and every node reports its version on its own, so a validator without one at round time is unusual rather than unlucky. `MINIMUM_SAFE_VERSION` must be a plain final release such as `1.0.8`; anything else stops the service at startup instead of silently disabling the rule. An empty value disables the rule and every verdict is `false`.
2. **One penalty-policy line.** The PENALTY POLICIES block gains the rule: `fails_minimum_safe_version: true` means the software sub-score is exactly 0, the reasoning names it, the field is taken as given, no other sub-score is affected, and a false value has no effect. The user prompt's data description names the field.

## Validation methodology

`scripts/replay_prompt_variants.py` gains a `v11` variant (template `scoring_v11.txt`, hidden `unl`, flag injection as for v10). A round frozen before v11 carries no verdict, so the variant computes it from `--minimum-safe-version` with the collector's own function, refusing to render when the argument is missing rather than silently rendering every validator as safe. The argument is also refused where it would be ignored — a variant that computes no verdicts, or a round that already carries them — and when it is not a plain final release. The data-fidelity gates treat the builder-added verdict the way they treat the v10 flags: rebuilt entries are compared against the frozen entries modulo exactly that key on rounds frozen before v11. Run outputs record the failing master keys (`validators_failing_minimum`), and the compare stage reports any of them whose software sub-score is not 0 and splits per-dimension drift by failing validators versus the rest.

**Testnet round 23** (2026-09-15, frozen under v10) was replayed against the pinned production runtime with the frozen request's own sampling parameters, using the round's published production response as the baseline:

- **Minimum safe version 1.0.6** — 54 validators, 11 on 1.0.6 and 43 below it (40 on 1.0.4, 2 on 1.0.0, 1 on 1.0.5): the shape the rule exists for, with most of the UNL on an unsafe release.
- **Minimum safe version 1.0.0** — the same round with nobody failing: the control shape, where the rule must change nothing it owns.
- **No reported version** — round 23 has no validator without a version, so a copy of the round was edited for this case only: the `server_version` of two validators on 1.0.6 (`v010`, `v025`, both with verified domains) was blanked in the frozen evidence and in the frozen request alike, and the copy was replayed with the minimum at 1.0.6.

## Iteration findings

**The rule lives in the penalty policies, not in the dimension text.** The first wording added two bullets to the SOFTWARE DILIGENCE dimension plus the penalty-policy line. It zeroed every failing validator but also moved every other validator's software sub-score from 100 to 90, although their reasoning still called the software current. Keeping the dimension text byte-identical to v10 and stating the rule once, in the penalty policies, leaves those validators at their production values.

**The verdict must be a true-valued warning.** The field was first rendered as `meets_minimum_safe_version`, with `false` triggering the penalty. Under otherwise identical wording the model zeroed only 9 of 43 failing validators and gave the other 34 a software sub-score of 80. Rendered as `fails_minimum_safe_version` with `true` triggering it, the same request zeroes 43 of 43. The model follows a raised flag far more reliably than a lowered confirmation.

No superseded roll is committed.

## Results

Raw outputs: `docs/promptv11-replays/` — `r23_v11.json` (minimum 1.0.6), `r23_v11_nobody_fails.json` (the control), and `r23_v11_no_version.json` (the edited copy). A repeat of the first run returned byte-identical model content (content sha256 `d045620c…`). The numbers below come from the harness `compare` stage against the round's published production response (`outputs/model_response.json`, wrapped as the harness docstring describes) and from re-running the production parser, score formula v1, and selector over each output with the round's frozen selector context and `inputs/previous_unl.json`.

- **The rule holds exactly.** 43 of 43 failing validators score software 0, and all 43 reasoning strings name the minimum safe version. No other validator's reasoning mentions it.
- **A validator without a version fails too.** In the edited copy both blanked validators score software 0 with the rule named in their reasoning, alongside the 43 older ones: 45 of 45.
- **Software is otherwise untouched.** All 11 validators on 1.0.6 keep their production software sub-score of 100; in the control run all 54 software sub-scores equal production.
- **The verdict does not leak into consensus or identity.** Consensus mean |delta| is 0.00 in both groups and identity is at most 0.12.
- **Parses clean under the production parser.** 54 of 54 entries in every run, no errors, zero consensus-ceiling and band violations.
- **Reliability and diversity re-rolled, as they do on any prompt edit.** Reliability moved on 37 of 54 validators, all downward and in both groups alike (31 of 43 failing, 6 of 11 others; mean |delta| 5.00 and 5.45): a uniform 5-point step on 33, which stays inside the prompt's 95-100 guide for stable operation, and −35 or −20 on four validators whose losses sit almost entirely in the 30-day window. The control run, where nobody fails, moves the same kind of validator (−35 twice, −20 twice, +20 once), so this is roll sensitivity of the old-incident band rather than the verdict at work. It is still the revision's weakest result: the −35 placements (75 to 40) sit below the prompt's own 75-90 guide for an old, resolved incident, and they cost seats in both runs. Diversity took a uniform 10-point step on 39 validators and a 5-point step on 5 more — the documented noisiest surface.
- **Selection moves as intended.** With the minimum at 1.0.6, 17 of 20 seats match the published round: three validators on 1.0.6 take seats from three on 1.0.4, leaving 10 seats on unsafe versions instead of 13, with the UNL still at 20. Ten of the 11 safe validators are seated. The eleventh is one of the reliability movers above: at its production reliability of 75 it would be seated, and at this roll's 40 it scores 78 and clears no incumbent by the churn gap — a miss caused by roll noise, not by the rule.
- **The control is not a perfect no-op for selection.** Its UNL matches the published round on 18 of 20 seats. The differences come from the re-roll of the other dimensions (one incumbent's reliability dropping from 95 to 75), not from software, which is identical to production for all 54.

## Rollout

Devnet first with a manually triggered round, then testnet on its standing schedule, the v10 pattern. `MINIMUM_SAFE_VERSION=1.0.8` is set in both deploy workflows, so the rule takes effect with the first deployment that carries v11; run a dry run first (`docs/ScoringOperations.md`, Raise the Minimum Safe Version). The governance checker resolves scoring eras by the hash of the system prompt and fails closed on an unknown one, so `scoring-model-governance` needs its v11 rules row (identical to v10's) before any v11 round enters a governance exam; that repository's vendor-freshness check fetches `prompts/scoring_v11.txt` from the matching branch of this repository (`main`, `devnet`, `testnet`) and errors when the file is missing, so the row merges to each governance branch only after this revision reaches the same branch here.
