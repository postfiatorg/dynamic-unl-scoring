# Scoring Prompt v10 — VHS Agreement Data-Quality Flags

`prompts/scoring_v10.txt` replaces `scoring_v9.txt` as the active scoring prompt, shipping together with one request-assembly change: the per-window `incomplete` data-quality flag that the Validator History Service returns with every agreement window is now parsed (`scoring_service/clients/vhs.py`), carried on the `AgreementScore` evidence model (`scoring_service/models/scoring.py`), and rendered into each validator entry's three agreement windows — always present, as `true`, `false`, or `null`. `PROMPT_VERSION` in `scoring_service/services/ipfs_publisher.py` moves to `v10`, so execution manifests pin the new template by path, version, and content hash as before. Score formula v1, its weights, the selector, and churn control are unchanged; `scoring_v9.txt` is retained on disk for audit; validator sidecars require no action because they replay the foundation's frozen `model_request.json` verbatim.

## Motivation

VHS computes each window's flag from its own observation quality: an hourly bucket is flagged when VHS's recorded ledger stream had gaps or the chain was newly tracked, and a rolling window is flagged when too many hourly buckets are missing (below its coverage threshold, typical for newly tracked validators or VHS downtime) or too many of the present buckets were themselves flagged. The scoring service dropped the field at parsing, so the model judged every window as if the measurement behind it were fully trustworthy: a validator with thirty minutes of perfect-but-thin history read the same as one with a month of it, and there was no way to tell degraded validators from degraded measurement.

The prompt semantics are deliberately one-directional, because the flag itself is trustworthy in only one direction. A raised flag reliably means "this window may be missing frames." An absent flag guarantees nothing: VHS scores absent validators with full missed counts and `incomplete: false` by design (so offline scores decay), and a chain-level flag cannot see per-validator delivery bias. The prompt therefore instructs that a true flag lowers confidence — especially on small totals — while evidence present in a window always keeps full weight, and a false or null flag never raises a sub-score. Guidance is describe-only: no new enforceable scoring rules, so the governance checker's rules for v10 are identical to v9's.

## The v10 changes

1. **Flag propagation.** `_parse_agreement` keeps `incomplete` alongside `score`/`total`/`missed`; `AgreementScore` gains the optional field; the prompt builder renders it automatically in every entry (null when VHS supplied no flag). The flag also lands in each round's frozen `inputs/validator_evidence.json`, enriching the audit trail.
2. **The AGREEMENT DATA QUALITY FLAGS block.** A system-prompt section after the five dimensions explains what the flag measures, that unheard ledgers are already excluded from `total`/`missed`, and the one-directional confidence rule; the user prompt's data description names the field.
3. **Key-integrity output clause.** The response-format rules gain one sentence — restate the exact `validator_id` as each entry's key, never an empty, whitespace, or quote-character key — added after replay validation surfaced a deterministic corrupted-key roll (below).

## Validation methodology

`scripts/replay_prompt_variants.py` gains a `v10` variant (template `scoring_v10.txt`, hidden `unl`, flag injection). Pre-v10 frozen rounds were parsed without the flag, so the variant reconstructs per-window flags from the round's raw `vhs_validators.json` — the untouched VHS response archived in the frozen input package — refusing to render silently-null flags when the file is absent, and cross-checking every window's `score`/`total`/`missed` against the frozen evidence so a wrong round's archive fails loudly instead of injecting wrong flags. Rounds frozen under v10 already carry their flags in the evidence and skip injection. The data-fidelity gate is extended the same way `provider_family` was handled: rebuilt entries are compared against the frozen entries modulo the builder-added flag for rounds frozen before v10, so a v10 render must carry the frozen round's validator data verbatim plus exactly the flags; the `baseline` variant's byte-for-byte gate applies the same adaptation, since the builder now always renders flag keys that pre-v10 frozen requests cannot contain. The compare stage also splits per-dimension drift by flagged versus unflagged validators when raw VHS evidence is present.

Two v9-frozen rounds were replayed against the pinned production runtime with the frozen requests' own sampling parameters, using each round's published production response as the baseline (no baseline re-run needed for v9-frozen rounds):

- **Testnet round 17** (2026-08-04, the first live v9 testnet round): 53 validators, four carrying a true 30-day flag — including one currently offline validator, the no-excuse case that matters most.
- **Devnet round 323** (2026-07-29): 3 validators, every flag false — the all-false control shape, where v10 must be a no-op.

## Iteration findings — the corrupted-key clause

The first v10 wording produced a deterministic parse defect on round 17: the model keyed validator `v038`'s entry as the literal string `"' '"` (its scores and reasoning were correct under the corrupted key), reproduced byte-identically on a repeat (content sha256 `22f3d872…`). The production parser fails closed on exactly this (missing ID plus unknown ID), so shipping it would have risked a live failed round of the round-322 kind. A tightened flag-block wording re-rolled the response but reproduced the same defect at the same entry (sha256 `0a8f3d94…`) — evidence the defect was data-positional, not phrasing luck, and the same single-corrupted-key mode the v9 iteration saw once in an intermediate roll. The fix that held is the scoring-semantics-free key-integrity clause in the response-format rules; with it the roll is clean at every entry. Neither superseded roll is committed; both shas are recorded here for the audit trail.

## Results

Raw outputs: `docs/promptv10-replays/` — `r17_v10.json` with byte-identical `r17_v10_repeat.json` (content sha256 `de164376…`), `r323_v10.json`, the two wrapped production baselines, and `machine-checks.txt` (the harness compare output over the committed runs).

- **Control round is a no-op.** Devnet 323: zero drift in all five dimensions, 0/3 final scores moved, no ceiling or band violations.
- **Round 17 parses clean under the production parser.** 53/53 entries, correct keys, zero errors; zero consensus-ceiling violations under the tolerance check and zero band violations.
- **Untouched dimensions stay put.** Unflagged validators (n=49): consensus, software, and identity mean |delta| all 0.00 against production v9; reliability 1.02 (single band steps).
- **No excusing.** Two of the four flagged validators score identically to production in every dimension — including the one that matters most: the offline validator keeps consensus 0 and reliability 10, its true 30-day flag buying it nothing, and the weakest-coverage flagged validator (181k-ledger 30-day window) is unchanged too. The other two moved only with the roll: one dropped a single diversity band (50→45), and one — the second-best 30-day record in the round with clean recent windows — moved consensus 99→100 (the documented fractional-top resolution, inside the one-point tolerance) and reliability 90→100, the same placement its unflagged evidence-peers hold in this roll (the healthy incumbent reliability mean is 100.0, and the count of validators at reliability 100 went 34→35 round-wide). No degraded evidence was softened anywhere.
- **No penalizing.** No flagged validator was marked down for carrying a flag: the only downward flagged moves are one 5-point diversity band step each on the two healthy movers, matching the round-wide diversity re-roll. The flagged reliability mean |delta| of 2.50 versus 1.02 unflagged is entirely that one 90→100 recalibration mover spread over four validators, not a systematic flag effect in either direction.
- **Diversity band placement remains the noisiest surface**, as documented for v9: unflagged diversity mean |delta| 6.22, ordering-consistent where checked (the HOSTKEY-US validator stays strictly above the Hetzner-US validator). Deterministic diversity remains the roadmap's guarantee-grade fix.
- **Selection: 19 of 20 seats identical; the one difference is churn control working as designed** (the re-run is recorded in `machine-checks.txt`'s selection section: production parser, score formula v1, and selector over `r17_v10.json` with the round's frozen selector context and `inputs/previous_unl.json`). Production v9 gave the HOSTKEY-US challenger a 9-point margin over the lowest Hetzner-US incumbent (≥ the 5-point churn gap → challenger seated); the v10 roll's band placement compresses that margin to 3 (92 vs 89, < gap → incumbent retained). Both outcomes are evidence-fair; this is the same boundary roll-sensitivity recorded in the v9 revision for round 16, resolved by the churn gap's continuity default.

## Rollout

This revision lands on `main` only. Devnet and testnet deployments are deliberately excluded and follow a separate decision; when rolled out, the first v10 rounds should follow the v9 pattern — devnet first with a manually triggered round, then testnet on its standing schedule — and the governance rules table gains its v10 row (identical to v9's) at that point.
